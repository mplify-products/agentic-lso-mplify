Agentic LSO Blueprint · Scope
What is inside Agent.Fergie.1
Contract
Per-API MCP profiles
A machine-checkable contract per API: tool name = OpenAPI operationId, strict 1:1 mapping, no composite tools. This is the concrete answer to the Reference Architecture's typed-interface requirement.
Agent
mplify-l2-agent
The worked L2 Orchestrating Agent: persona, business process and cross-API rules written as platform-neutral Markdown plus a manifest. Proven in three runtimes — a web agent, Claude Code and Copilot.
Knowledge
Skills and knowledge packs
One skill and one knowledge pack per API, served as MCP resources with phase-scoped progressive disclosure. Content is served verbatim and read before every payload — the control against hallucinated requests.
Servers
Eight MCP servers
A reference runner generates tools, resources and prompts straight from the OpenAPI spec — eight containers, one per API. Deterministic projection, no embedded reasoning.
Payloads
Internet Access, Mplify 139.1
Complete: guide, schema, examples and validation rules. Carrier Ethernet is a registry stub only — Internet Access is the pattern the rest will be built to.
Conformance
LSO Conformance Test Kit
Validates a live deployment against its declared profile and the truthfulness of its capability statement. The Reference Architecture has no conformance layer yet — this is a candidate input.
Deferred, on purpose. Appointment (MEF 137), Work Order, Billing, and Product Offering Availability & Pricing are present in the SDK and listed under deferred: in the version manifest. Service-layer APIs and day-2 operations are out of scope for this release — Agent.Fergie.1 is Product layer only.
Since Lisbon · In progress
Major progress since Lisbon
01
Security — the Agent → MCP scope
  • Capability-scoped tool surface. Operations a Seller does not support are not exposed as tools at all.
  • Untrusted content handled as untrusted. A dedicated trust-boundary skill, plus code-level injection scanning and data-wrapping of every tool result and resource.
  • Transport and credentials. TLS off loopback, host allowlist, header or bearer auth, no hardcoded secrets, secret scanner in the commit hooks.
Still open: the model gates its own actions — no authorisation / execution split, no mutual authentication of the calling agent.
02
Trouble Ticketing added
  • MEF 124 Trouble Ticket & Incident ships as a lifecycle branch off Product Inventory.
  • Includes Seller-declared incidents, not only Buyer-raised tickets.
  • The first assurance flow in the Blueprint — everything before it was fulfilment.
  • Same treatment as the fulfilment APIs: skill, knowledge pack, conformance profile and MCP server.
Order-to-ticket is now one continuous conversation.
03
The Capability Statement
  • A per-Seller declaration of which APIs, operations, options and products that Seller actually supports.
  • Read before any workflow starts — the agent never guesses what is on the other side.
  • The tool list becomes a testable projection of the declaration.
  • Not in Agent Reference Architecture v2 — a candidate input to the next revision.

Contract · Beyond Architecture v2
The Seller Capability Statement
Onboarding used to be a project.
Now it is a single request.
Which APIs this Seller runs, which operations, which options, which products — discovery that used to mean weeks of specification reading, e-mail threads and trial integration before the first call could be made. The agent asks once, and gets a machine-readable answer.
01
One resource, read first. mplify://capabilities is fetched before the agent asks the Buyer anything. It declares APIs and versions, the operations supported on each, optional behaviours, and the products actually orderable.
02
The tool surface is a projection of it. An operation the Seller does not support is not exposed as a tool. The agent cannot call what does not exist, so it cannot invent a flow the Seller cannot fulfil.
03
It is testable. The Conformance Test Kit checks the live deployment against its profile and checks that the statement tells the truth — a declared operation that 404s is a conformance failure.
04
It makes partial adoption safe. A Seller that has implemented four of the seven fulfilment APIs declares four. The same agent works against them without configuration, and degrades honestly rather than failing late.

Adoption · Deployment topologieshover a diagram, or step them with the arrows
Same bricks, four different deployments
Agent.Fergie.1 ships one L2 agent, eight MCP servers, skills, knowledge packs and a capability statement. None of those bricks care which side of the trust boundary they run on — so the same release already runs in four of the Architecture’s deployment scenarios, unchanged.
01 · Scenario 1
The Seller hosts the whole stack
The same agent and the same eight servers, moved behind the Seller’s own front door — so a Buyer with no agent at all still gets the whole flow, over a portal or a person. Nothing in the artifacts changes; only who runs them.
02 · Scenario 3
The Buyer’s agent, the Seller’s MCP servers
The reference arrangement, and the one the CTK measures. One agent, eight Seller MCP servers, proven in three runtimes — a web agent, Claude Code and Copilot. Every other tile on this slide is this one, rehoused.
03 · Scenario 2
The Buyer hosts the whole stack
The reference runner projects MCP servers straight from the Seller’s published OpenAPI spec, so the Buyer runs them itself and the Seller changes nothing — not even the capability statement: the Buyer writes its own capability configuration to match the API it is pointed at.
04 · Scenario 5
A broker hosts the stack in the middle
A broker, aggregator or marketplace runs the identical stack and resells it. It works because the bricks are position-neutral: the Seller sees an ordinary MCP client, the Buyer an ordinary agent, and what the broker adds on top is its own business.
Rearranging is free; new channels are not. These four differ only in where the boundary is drawn — the agent, the servers and the knowledge packs are byte-identical. The two scenarios that do not assemble need bricks that do not exist yet: Scenario 4, Buyer agent to Seller agent over A2A (no channel, no agent card), and Scenario 6, one Buyer across many Sellers (configuration binds to a single Seller).

Enterprise onboarding — from zero to first order
The barrier that has kept smaller Buyers off LSO was never the standard — it was the integration project. An enterprise with no API integration, too small to ever justify starting one, can now stand up a working integration with an LSO-exposing Seller almost instantly.

Adoption · The inter-provider business problem
Agentic LSO for ASR
Access Service Request (ASR) ordering between providers is already digital, but the time and money go into the gaps: waiting, reworking and missed dates. Published estimates put fallout on complex inter-carrier orders at 20–35% and quote-to-activation at 30–60+ business days. Here is how Agent.Fergie.1 addresses each gap, working through the LSO APIs that already exist.
01 · Quoting
A quote is a separate process that takes 24 to 72 hours
A valid address still does not say whether capacity exists. The agent runs address validation, Product Offering Qualification (POQ) and Quote as one conversation, so the Buyer gets availability and price together, while the deal is still open.
02 · Fallout
One wrong field stops the order
Code mismatches, address mismatches and new-or-existing handoff questions are caught before submission. The agent checks the order against the Seller’s product catalog and site data first, so the Seller receives fewer orders it has to reject and re-work.
03 · Visibility
You find out after you’ve promised a date
Product Order, Product Inventory and Trouble Ticket are in the same agent, so the Buyer can ask where the order is, what is installed and whether it is working at any point, instead of waiting hours for an error to come back.
04 · Scale
Every partner is a separate build
The agent is built once, to the Mplify LSO standard, and reused with every partner. The Buyer can generate the MCP servers from a Seller’s published API specification, so neither provider changes its own systems to add a partner.
What it does not fix. An agent at the front door does not change what happens behind it: ordering and visibility improve first, and delivery only gets faster when the systems behind the API change too. People keep the judgment calls and the exceptions. Buyer-agent to Seller-agent over A2A is not in this release.
New project · MP0188 · Vodafone and partners
Agentic cyber security — closing the loop
Threats between Service Providers and their Customers are still handled through disjointed workflows and manual hand-offs, from detection to mitigation — and every delay is exposure. MP0188 applies Mplify LSO standards and Agentic AI to detect, report and block threats in one closed loop.

Blueprint roadmap · Three axes of evolution
What comes after Agent.Fergie.1
Agent.Fergie.1 sits at the origin. Three directions lead out of it, and they are independent — work on one does not have to wait for another. Which axis moves first is the question for the room.
Axis 1 · the agent
Deepen the stack
Asynchronous communications first — the Blueprint is poll-only by decision D17 — then A2A, the L3 agent, DIDs and verifiable credentials, and finally the L1 agent and observability.
Axis 2 · the APIs
Widen the coverage
The same release, more of it. The fulfilment chain and Trouble Ticket are covered; Incident, Menu-Driven Ordering, Billing, CIM, Appointment and Work Order are not.
Axis 3 · the SDK
Move the release target
The name binds the Blueprint to one API set. Re-targeting a later LSO SDK release is a third, independent direction — which release, and when, is open for member input.
